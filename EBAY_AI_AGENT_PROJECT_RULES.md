# 1. Главная цель

Создавать максимально стабильное, быстрое, удобное, экономичное, точное и простое в поддержке расширение для автоматизации eBay и других маркетплейсов.

Решение оценивается одновременно по:

- стабильности;
- скорости;
- удобству;
- точности;
- стоимости AI/API;
- простоте кода;
- простоте поддержки;
- безопасности.

Не улучшать один показатель ценой серьёзного ухудшения остальных.

Если заметное ускорение повышает риск сбоев — предпочитать более стабильный вариант.

Если более дорогой AI/API-подход даёт лишь небольшое улучшение качества — предпочитать более дешёвый и быстрый вариант.

Безопасность, сохранность данных, защита секретов и запрет неожиданных необратимых действий не должны приноситься в жертву балансу.

---

# 2. Основной рабочий цикл

Для любой существенной задачи:

```text
понять задачу
→ изучить актуальный код
→ найти проблемные места
→ определить root cause или наиболее вероятную причину
→ проверить зависимости
→ сравнить решения
→ выбрать лучший вариант
→ исправить
→ проверить
→ при необходимости доработать
→ повторно проверить
→ передать законченный результат
```

Не начинать изменение с первой догадки.

---

# 3. Уровни уверенности анализа

Не выдавать предположение за доказанный факт.

Использовать:

- **Подтверждено** — причина доказана кодом, логами, тестом или воспроизведением.
- **Вероятно** — есть сильные признаки, но полного доказательства нет.
- **Неизвестно** — данных недостаточно.

Особенно осторожно анализировать динамический DOM, React-события, drag-and-drop, загрузку фото, race conditions, сетевые запросы и browser timing.

Если есть несколько возможных причин одной проблемы, сначала сузить их до наиболее вероятной или подтверждённой. Не исправлять сразу все гипотезы.

---

# 4. Дополнительные данные

Сначала максимально использовать уже доступные данные и доступные средства анализа.

Не просить ZIP, DOM, логи, запись экрана или дополнительные материалы «на всякий случай».

Запрашивать дополнительные данные только если без них:

- нельзя достаточно надёжно определить причину;
- риск неправильного исправления заметный;
- безопасная аналитическая или диагностическая попытка не дала достаточной уверенности;
- невозможно проверить ключевое предположение;
- невозможно продолжить работу.

Полезные дополнительные данные, когда они действительно нужны:

- актуальный ZIP;
- DOM/HTML проблемной области;
- Console errors;
- логи;
- скриншоты;
- запись экрана;
- точные шаги воспроизведения;
- ожидаемый результат;
- фактический результат;
- дополнительные фотографии товара.

# 5. Большие задачи

Для задач уровня «полностью проверь расширение», «сделай стабильнее», «ускорь всю систему», «найди все серьёзные проблемы» сначала проводить полный аудит всего релевантного проекта.

Перед исправлениями понять:

- какие проблемы существуют;
- где root causes;
- какие симптомы являются следствиями;
- какие модули зависят друг от друга;
- что блокирует другие исправления;
- что опасно менять;
- какие проблемы можно объединить;
- в каком порядке лучше работать.

Не начинать большой аудит с первой очевидной проблемы, если это может привести к локальному костылю без понимания общей причины.

Если большая задача уже согласована, после аудита не требуется отдельная остановка только ради утверждения списка найденных проблем. Можно переходить к исправлениям в рамках согласованной задачи.

**Исключение:** серьёзная архитектурная переделка, существенный выход за рамки задачи или неоднозначное продуктовое решение всё равно требуют отдельного согласования.

# 6. Порядок исправлений

Исправлять проблемы в порядке реального влияния и зависимостей:

1. root causes;
2. критичные проблемы стабильности;
3. проблемы правильности работы;
4. зависимости, блокирующие другие исправления;
5. серьёзные race conditions;
6. производительность;
7. удобство;
8. менее серьёзные дефекты;
9. чистка и упрощение кода.

**Безопасность не является обычным пунктом очереди.** Защита секретов, сохранность данных, разрешённая область действий и запрет неожиданных необратимых действий проверяются на каждом этапе и могут остановить любое изменение.

Если критичная проблема зависит от более низкоуровневого дефекта — сначала исправить эту зависимость.

Не идти по файлам просто сверху вниз.

# 7. Root cause важнее симптома

Не маскировать проблему дополнительными:

- `sleep()`;
- случайными timeout;
- бесконечными retry;
- лишними `MutationObserver`;
- повторными кликами;
- постоянными полными DOM-сканами.

Предпочтительный принцип:

```text
проверить состояние
→ выполнить действие
→ подтвердить результат
→ продолжить
```

Timeout — максимальный предел ожидания, а не обязательная задержка.

---

# 8. Выбор решения

Если один технический вариант явно лучше — самостоятельно выбрать его и кратко объяснить причину.

Не перекладывать очевидный технический выбор на пользователя.

Показывать несколько вариантов только когда они действительно сопоставимы или имеют существенно разные риски/последствия.

Предложение пользователя нужно технически оценивать. Если вариант создаёт костыль, нестабилен, слишком сложен или заметно хуже альтернативы — предложить лучший.

---

# 9. Существующий код и переписывание

По умолчанию сохранять и улучшать существующую рабочую реализацию.

Не переписывать систему с нуля только потому, что новая архитектура выглядит красивее.

Серьёзная переделка оправдана, если текущая реализация реально мешает стабильности, скорости, точности, удобству, безопасности, тестируемости или поддержке.

Перед существенной переделкой отдельно объяснить:

- почему локального исправления недостаточно;
- что даст переделка;
- какие риски;
- что будет затронуто.

После согласования переделывать правильно.

---

# 10. Патчи

Количество патчей определяется не количеством проблем, а тем, как безопаснее и логичнее их исправить.

### Объединять

Маленькие связанные проблемы можно объединять в один патч, если:

- они находятся в одной области;
- имеют общую причину или тесную связь;
- их удобно проверить вместе;
- объединение не повышает риск регрессий.

### Разделять

Крупные, независимые или рискованные изменения делить на несколько патчей, если объединение усложняет проверку или поиск причины новых ошибок.

Предпочитать минимально необходимое число патчей, чтобы не засорять чат и историю проекта.

---

# 11. Что можно исправлять без отдельного согласования

После согласования задачи можно самостоятельно исправлять мелкие связанные дефекты, найденные по ходу работы, если они:

- находятся в той же области;
- имеют понятную причину;
- не меняют согласованное поведение;
- не расширяют существенно задачу;
- не повышают риск.

Все дополнительные исправления перечислять в итоговом отчёте.

Отдельное согласование нужно для крупной, спорной, несвязанной или архитектурно рискованной проблемы.

---

# 12. Доведение до готовности

После согласования задачи не останавливаться после первого цикла исправления.

Самостоятельно повторять:

```text
исправление
→ глубокая проверка
→ дополнительное исправление
→ повторная проверка
```

столько раз, сколько разумно необходимо для законченного результата.

Если пользователь просил готовую сборку/ZIP, не отдавать заведомо промежуточную версию как готовую.

Частичный результат допустим только при реальном блокере, который невозможно устранить в текущей среде. Блокер нужно явно указать.

---

# 13. Рабочий соседний код

Не менять рабочий соседний код только потому, что его можно сделать красивее.

Улучшать его в текущем патче только если это прямо повышает стабильность, скорость, точность, удобство, безопасность или заметно упрощает поддержку текущей задачи.

---

# 14. Dead code

Если доказано, что код больше не используется, дублирует активную реализацию или является старым временным fix, его можно удалить в том же патче без отдельного согласования.

После удаления обязательно проверить связанные функции и регрессии.

Не хранить backup-копии production-кода внутри проекта. Для истории использовать Git и предыдущие ZIP.

---

# 15. Простота архитектуры

Простой код лучше сложного при одинаковом результате.

Не создавать:

- абстракцию ради абстракции;
- слой, класс или сервис без необходимости;
- сложную универсальную систему «на будущее»;
- лишний контейнер ради одной маленькой функции.

При этом решение не должно быть тупиковым: его должно быть разумно расширить позже.

```text
Simple > Clever
```

---

# 16. Функции, модули и контейнеры

Нет правила «большая функция всегда плохая» или «много маленьких функций всегда хорошо».

Разделять код, когда это реально улучшает:

- понятность;
- тестируемость;
- повторное использование;
- изоляцию ошибок;
- стабильность;
- поддержку.

Оставлять последовательную логику вместе, если дополнительное дробление только усложняет систему.

Каждый основной модуль или контейнер должен иметь **одну понятную ответственность/операцию**. Не смешивать несколько независимых функций в одном контейнере.

Сложный сценарий лучше строить как последовательность небольших понятных операций, если такое разделение реально уменьшает сложность, а не создаёт её.

# 17. Базовая архитектура

Предпочтительная логическая цепочка:

```text
Collector
→ Image/OCR
→ Analysis
→ Answer Normalizer
→ Fill Engine
→ Verification
```

Дополнительные части:

```text
Platform Adapter
Queue
UI
Storage
Logging
API Client
```

Не смешивать независимые функции в одной огромной реализации.

---

# 18. Одна логика вместо копий

Одинаковая операция должна иметь одну основную реализацию.

Пример:

```text
Photo → Answers → Fill Engine
Text → Answers → Fill Engine
Queue → Answers → Fill Engine
```

Hotkey должен вызывать ту же команду, что и кнопка.

Общие правила, конфигурации и списки исключений должны иметь один источник истины.

---

# 19. Platform Adapter

Общая логика должна быть максимально общей.

Особенности eBay, Depop, Poshmark, Vinted и будущих платформ должны быть изолированы в `Platform Adapter`.

Новая платформа не должна требовать копирования всего Collector, AI, Fill Engine, Queue и Verification.

Adapter содержит только действительно платформенные различия.

---

# 20. AI, OCR и обычный код

### AI использовать для

- анализа фотографий;
- понимания товара;
- неоднозначной классификации;
- сложного извлечения смысла;
- выбора наиболее вероятных характеристик.

### OCR использовать для

- извлечения наблюдаемого текста с изображений;
- чтения этикеток и маркировок;
- получения структурируемых наблюдаемых данных.

Низкоуверенный OCR не должен автоматически превращаться в уверенный факт. Если распознавание сомнительное и значение важно, нужен дополнительный сигнал или проверка.

### Обычный код использовать для

- DOM;
- deterministic matching;
- кликов;
- установки значений;
- проверки;
- Queue;
- storage;
- state machine;
- permissions;
- deterministic post-processing.

AI не должен напрямую управлять DOM командами типа «нажми третью кнопку».

AI определяет **что** должно быть заполнено, а Fill Engine определяет **как** безопасно применить решение.

# 21. AI output

Предпочтительный формат:

```json
{
  "answers": [
    {
      "field": "Color",
      "values": ["Blue"]
    }
  ]
}
```

После AI-ответа обязательно:

- проверить schema;
- удалить запрещённые поля;
- проверить типы;
- удалить дубликаты;
- проверить allowed options;
- безопасно обработать пустые и невалидные значения.

AI может ошибаться даже при строгом prompt.

Prompt должен быть структурированным и передавать только нужный контекст:

```text
product context
→ relevant photos/OCR
→ requested fields
→ allowed options
→ output schema
→ active rules
```

Не использовать свободный хаотичный текст, если задачу можно выразить стабильным контрактом.

# 22. Точность, полнота и риск

Политика ниже относится прежде всего к режимам, где результат **обязательно проходит ручную проверку**.

Для таких режимов цель для разрешённых обычных Item Specifics — заполнить как можно больше полей максимально близко к правильному ответу.

### Низкий риск

Можно использовать наиболее вероятное разумное значение, даже если уверенность не абсолютная.

Примеры: Color, Pattern, Theme, Season и обычные style attributes.

### Средний риск

Нужны более хорошие основания.

Примеры: Material, Size, Model, Department и похожие характеристики.

### Высокий риск

Не угадывать без достаточных оснований.

Примеры: authenticity, юридически значимые данные, опасные поля, необратимые действия.

Риск-политика применяется только к тем полям и действиям, которые конкретный режим вообще имеет право менять.

Если в будущем появится режим без обязательной ручной проверки, для него должны быть заданы более строгие пороги отдельно.

AI confidence сам по себе не является доказательством.

# 23. Разрешённая область действий: allowlist по умолчанию

Каждый режим должен иметь явный **allowlist** того, что ему разрешено читать и изменять.

Всё, что не разрешено явно, считается запрещённым по умолчанию.

AI-ответ не может расширять allowlist.

Особенно защищать:

- Title;
- Description;
- Condition;
- Category;
- Price;
- Quantity;
- Shipping;
- UPC;
- MPN;
- Publish;
- Delete;
- Purchase;
- Payment.

Конкретный allowlist зависит от режима и платформы.

# 24. Контракты данных, состояние и single source of truth

Функция должна ясно показывать:

- что получает;
- что возвращает;
- что может изменить;
- какие статусы и ошибки возможны.

Предпочитать структурированные входы/выходы вместо скрытого глобального состояния.

Внешние данные из DOM, AI, OCR, storage, API и backend нужно валидировать на границе системы. После валидации внутренние модули должны работать с одним согласованным форматом.

Для каждого важного правила или состояния должен быть один источник истины:

- statuses;
- permissions/allowlist;
- excluded fields;
- configuration;
- field policy;
- queue state.

Не размазывать одинаковые списки и правила по Photo, Queue, Text, Review и другим режимам.

Минимизировать глобальное изменяемое состояние. Если данные нужны нескольким модулям, передавать их явно или хранить в одном контролируемом state.

Не мутировать входные данные неожиданно, если их используют другие части системы.

Контракты между общими модулями должны быть стабильными. Не поддерживать одновременно несколько случайных форматов одного и того же результата внутри каждого модуля. Если нужна совместимость со старым форматом — преобразовывать его в одном входном адаптере.

Сохранять архитектурные инварианты, например:

- Fill Engine не вызывает AI;
- AI не расширяет allowlist;
- Text-режим не требует фотографий без причины;
- Queue не имеет собственного дубликата Fill Engine.

В development/test допустимы assertions для раннего обнаружения нарушения таких инвариантов.

# 25. Matching

Нормализация и fuzzy matching — разные вещи.

Допустимо:

```text
" Long Sleeve " → "long sleeve"
```

Но нельзя автоматически считать:

```text
Sweatshirt ≈ Hoodie
```

если политика требует точного совпадения.

Fill Engine должен быть детерминированным там, где это возможно.

---

# 26. DOM и React

Предпочитать устойчивые признаки:

- label;
- field name;
- aria attributes;
- semantic relationships;
- стабильные контейнеры.

Не полагаться без необходимости на хрупкие `nth-child` selectors.

Искать элементы внутри правильной области.

Учитывать, что React может заменить DOM-элемент. Проверять `element?.isConnected` или заново находить конкретный элемент после перерисовки.

При необходимости использовать native setter + `input/change/blur`, а затем verification.

---

# 27. Success только после verification

Отсутствие exception не означает успех.

Правило:

```text
действие
→ локальная verification результата
→ FILLED / ALREADY_SET / REVIEW / FAILED
```

UI не должен показывать успех, пока значение фактически не установлено.

Если значение уже правильное — не устанавливать его заново, не снимать и не дублировать.

### Batch не отменяет локальную проверку

Оптимальная схема может быть пакетной:

```text
1 snapshot
→ 1 analysis
→ batch execution с локальной проверкой
→ final verification
```

но каждое изменяемое поле всё равно должно получить достаточную локальную проверку успеха.

Итоговая verification дополняет локальную, а не заменяет её.

# 28. Retry и ошибки

Retry должен быть:

- ограниченным;
- локальным;
- направленным на конкретную проблему;
- отменяемым после успеха.

Не использовать бесконечные циклы.

Различать:

- FIELD ERROR;
- DRAFT ERROR;
- PAGE ERROR;
- PROCESS ERROR;
- CRITICAL ERROR.

Ошибка одного поля обычно не должна останавливать остальные поля.

Ошибка одного товара обычно не должна уничтожать всю Queue.

Ошибки должны быть структурированными и объяснять причину.

Не использовать пустые `catch {}`.

---

# 29. Idempotency, pure logic и control flow

Повторный запуск операции по возможности не должен ломать уже правильный результат.

Перед изменением проверять текущее состояние. Если ожидаемое значение уже установлено — возвращать `ALREADY_SET` и не выполнять лишнее действие.

По возможности отделять pure logic:

```text
normalizeAnswer()
parseResponse()
validateAnswer()
matchOption()
```

от side effects:

```text
click()
setInputValue()
fetch()
chrome.storage.set()
```

Предпочитать предсказуемый последовательный control flow и `async/await`, если это делает процесс понятнее.

Избегать хаотических цепочек:

```text
callback → timer → observer → async loop → второй observer
```

---

# 30. Queue и долгие процессы

Любой длинный процесс должен:

- иметь явное состояние;
- не запускаться дважды;
- корректно реагировать на Stop;
- не запускать новые действия после остановки;
- по возможности отменять ненужные сетевые запросы;
- не ломать всю очередь из-за одного товара.

По возможности после перезапуска или сбоя система должна понимать, где остановилась, и безопасно продолжать.

Предпочитать один понятный state machine вместо нескольких конфликтующих boolean.

---

# 31. Производительность

Сначала определить реальное узкое место.

Сокращать:

- повторные DOM-сканы;
- лишние AI/API calls;
- фиксированные ожидания;
- повторную обработку одинаковых данных;
- ненужные UI updates;
- лишние save cycles.

Где безопасно:

```text
1 snapshot
→ 1 analysis
→ batch execution с локальной проверкой
→ final verification
```

Кэшировать только то, что безопасно кэшировать. Например, options можно кэшировать на время текущего draft, но нельзя долго хранить stale DOM-ссылку после перерисовки страницы.

Если заявляется серьёзное ускорение — по возможности измерить его.

---

# 32. Стоимость AI/API

Перед добавлением нового AI/API-запроса сначала проверить, нельзя ли получить тот же результат через:

- обычный код;
- OCR;
- уже собранные данные;
- предыдущий AI-анализ;
- кэш текущей операции;
- deterministic matching.

AI/API использовать там, где он действительно повышает качество.

При одинаковом или почти одинаковом результате выбирать более дешёвый и быстрый вариант.

Экономия не должна заметно ухудшать точность или стабильность.

---

# 33. Temporary hacks

Production-код должен использовать устойчивое решение.

Временный костыль допустим только для диагностики или короткого эксперимента.

Перед релизом временный код нужно удалить или заменить нормальной реализацией и повторно проверить систему.

Для действительно рискованной новой функции допустим временный feature flag, если он облегчает безопасный rollout/тест. После стабилизации старый путь и ненужный flag нужно удалить.

---

# 34. Очистка ресурсов

После завершения или отмены операции очищать созданные ресурсы:

```text
observer.disconnect()
clearTimeout()
clearInterval()
abort unused request
remove temporary listener
```

Если операция завершилась раньше timeout — timeout должен быть отменён.

Не оставлять бесконечные observer/interval без доказанной необходимости.

Очистка ресурсов — обязательная часть стабильности, а не необязательная оптимизация.

---

# 35. Сетевые запросы и устойчивость API

Каждый важный сетевой запрос должен иметь:

- разумный timeout;
- понятную обработку отмены;
- классификацию ошибок;
- ограниченный retry только для подходящих временных ошибок.

Пример:

```text
401 → authentication
429 → rate limit
5xx → provider/server
timeout → network
invalid JSON → parsing
```

Не повторять заведомо постоянную ошибку как временную.

Для временных сетевых ошибок можно использовать ограниченный backoff.

Дорогие AI/Vision вызовы нельзя повторять бесконечно.

---

# 36. Backward compatibility и storage

После небольшого патча существующие рабочие режимы должны продолжать работать.

Например:

- изменение Queue не должно неожиданно ломать Text;
- изменение UI не должно ломать Analysis;
- изменение Platform Adapter не должно менять общую логику без причины.

Если меняется формат storage/settings:

- читать старый формат;
- безопасно мигрировать;
- не терять существующие настройки;
- проверять backward compatibility.

Не менять стабильный внутренний контракт модуля без необходимости.

---

# 37. Dependencies и качество сборки

Использовать минимально необходимое количество dependencies.

Каждая dependency добавляет размер, supply-chain risk, обновления, несовместимости и дополнительную поддержку.

Не устанавливать малоизвестную библиотеку ради нескольких простых строк без причины.

Использовать lockfile там, где есть package manager.

Не запускать автоматически непроверенный код из AI output, случайного issue/comment, неизвестного репозитория или веб-страницы.

Поддерживать единое форматирование и базовый linter, если проект использует соответствующий toolchain.

Не смешивать массовое форматирование с функциональным patch без необходимости.

---

# 38. Тестирование

После существенного изменения проверить:

- синтаксис;
- запуск;
- изменённую функцию;
- связанные функции;
- negative scenarios;
- регрессии;
- allowlist/запрещённые области;
- отсутствие утечки секретов;
- отсутствие неожиданных действий.

### Unit tests

Использовать для детерминированной логики:

- normalization;
- parsing;
- exact matching;
- multi-value splitting;
- validation;
- status calculation;
- field policies.

### Integration tests

Использовать для связок:

- Fill Engine + mock DOM;
- Photo → AI result → Fill Engine;
- Text → parser → Fill Engine;
- Queue → draft → Fill → verify;
- Platform Adapter + common engine.

### Negative tests

Проверять не только успешный путь, но и:

- поле отсутствует;
- option отсутствует;
- dropdown не открылся;
- DOM был заменён;
- AI вернул невалидный ответ;
- API timeout;
- пустой ответ;
- duplicate event;
- Stop во время работы;
- повторный запуск;
- partial failure.

### Regression tests


Если серьёзный исправленный баг **разумно воспроизводится автоматическим тестом, regression test обязателен**.

Если полноценный автоматический тест невозможен из-за реального eBay/Chrome:

1. создать максимально близкую автоматическую проверку;
2. зафиксировать реальный сценарий теста;
3. не называть browser-поведение полностью подтверждённым до фактического теста.

Если root cause исправлен и связанные симптомы исчезли, не менять их код без необходимости, но обязательно отдельно перепроверить каждый ранее найденный симптом.

---

# 39. Автоматическая и реальная проверка

Если функцию нельзя полноценно проверить без реального браузера:

- выполнить максимум доступных автоматических проверок;
- считать сборку технически готовой к реальному тесту;
- явно указать, что реальное поведение ещё не подтверждено;
- после реального теста при необходимости продолжить исправление.

Нельзя притворяться, что проверено то, чего проверить невозможно.

---

# 40. Логи и диагностика

Логи должны позволять восстановить ход процесса и найти root cause.

### Обычный режим

Логировать кратко:

- начало этапа;
- ключевой результат;
- warning;
- error;
- завершение.

### Debug mode

Можно логировать подробнее:

- состояния;
- входы/выходы модулей;
- matching;
- retry;
- verification;
- timings;
- причины решений.

Никогда не логировать:

- API keys;
- tokens;
- cookies;
- пароли;
- платёжные данные;
- другие секреты.

# 41. Debug snapshot и воспроизводимость

Использовать уровни логирования по назначению:

```text
DEBUG
INFO
WARN
ERROR
```

Production-лог не должен быть забит DEBUG-сообщениями.

Для сложных проблем полезно сохранять безопасный debug snapshot:

  "fields": [],

  "fillResults": []

Snapshot должен по возможности позволять воспроизвести ошибку без нового дорогого AI-call.

Для серьёзного бага желательно фиксировать:

- версию;
- режим;
- тип draft;
- входные данные;
- поле;
- AI/OCR результат;
- доступные options;
- ожидаемый результат;
- фактический результат.

Никогда не включать в snapshot секреты.

# 42. Безопасность

Не хранить секреты непосредственно в коде.

Использовать минимально необходимые permissions.

Критические и необратимые действия не должны происходить неожиданно или как побочный эффект другой функции.

Если режим не предназначен для Publish/Delete/Purchase/Payment — он не должен выполнять эти действия.

---

# 43. Чистота кода

Использовать:

- понятные имена;
- `const` по умолчанию;
- `let` только при необходимости;
- `===` / `!==`;
- constants вместо magic values;
- структурированные statuses;
- централизованный config;
- комментарии, объясняющие «почему»;
- именованные constants/enums вместо непонятных magic values.

Избегать:

- `var`;
- dead code;
- огромных `try/catch`;
- пустых `catch`;
- лишнего global state;
- copy-paste архитектуры;
- скрытых side effects;
- случайных числовых/строковых magic values, когда смысл должен иметь имя.

Комментарий не должен повторять очевидный код; он нужен для неочевидной причины, ограничения или особенности платформы.

Код должен быть самодокументируемым через понятные имена функций, переменных и статусов.

JSDoc/типизация полезны там, где они реально делают контракты яснее. Не мигрировать весь проект на новый type-system только ради одного локального бага.

---

# 44. Файлы, версии и структура

Версионирование:

- **PATCH** — исправления и небольшие улучшения;
- **MINOR** — новые функции и заметные изменения;
- **MAJOR** — крупные несовместимые изменения.

Одна сборка должна иметь одинаковую версию во всех основных местах.

Production содержит только актуальный код.

Тесты, `TEST_RESULTS`, `PATCH_NOTES` и записи по версиям хранить внутри папки `Tests`, чтобы корень проекта оставался чистым.

В корне оставлять только основные папки и файлы запуска/установки.

README должен объяснять актуальный запуск/установку, основные режимы и диагностику, а не служить архивом всех старых патчей.

Архитектурная документация должна соответствовать реальному коду. Если реализация изменила ключевой поток или контракт — обновить документацию в том же релевантном изменении.

Не создавать хаотичные production-файлы:

```text
final2.js
new_fix.js
old_real.js
backup_final.js
```

# 45. Итоговый отчёт после существенного обновления

Кратко сообщить:

### Что было не так
Сначала указать уровень уверенности: **Подтверждено / Вероятно / Неизвестно**.

Затем описать root cause или наиболее вероятную причину.

### Что изменено
Основные изменения.

### Почему выбран этот вариант
Чем он лучше альтернатив.

### Что проверено автоматически
Тесты и проверки.

### Что проверено реально
Указать только фактически выполненный browser/device test. Не переносить сюда предположения или результаты mock-тестов.

### Что ещё требует реальной проверки
Только если это невозможно проверить в текущей среде.

### Дополнительные исправления
Мелкие связанные дефекты, исправленные по ходу.

### Результат
Готовая версия / ZIP, если это было частью задачи.

# 46. Самостоятельность ИИ

После согласования задачи ИИ должен максимально самостоятельно использовать доступные средства анализа и проверки.

Не нужно:

- останавливаться без причины;
- просить пользователя делать то, что можно проверить самостоятельно;
- спрашивать разрешение на каждый маленький связанный fix;
- выдавать промежуточную сборку как законченную.

Нужно:

- доводить задачу максимально далеко в рамках доступной среды;
- самостоятельно выбирать явно лучший технический вариант;
- честно обозначать ограничения;
- различать подтверждённое, вероятное и непроверенное.

# 47. Короткий алгоритм для любой проблемы

Этот раздел — **чеклист**, а не отдельный набор правил. При расхождении действует полный раздел выше.

```text
1. Понять задачу.
2. Изучить актуальный код.
3. Найти все релевантные проблемные места.
4. Определить root cause или сузить гипотезы.
5. Проверить зависимости.
6. Выбрать лучшее решение по общему балансу.
7. Определить минимально необходимый объём изменений.
8. Исправить связанные мелкие дефекты в той же области.
9. Удалить доказанный dead code.
10. Проверить cleanup/cancellation, если затронуты async/DOM процессы.
11. Запустить автоматические проверки.
12. Перепроверить каждый исходный симптом.
13. Добавить regression test для серьёзного воспроизводимого бага.
14. Повторять fix → test, пока результат не станет законченным.
15. Подготовить реальный test scenario, если browser-проверка невозможна.
16. Передать готовую сборку и краткий отчёт.
```

# 50. Главное правило проекта

> Всегда искать решение, которое даёт лучший реальный результат для пользователя: высокий общий баланс стабильности, скорости, удобства, точности, стоимости, безопасности и простоты поддержки — с минимумом лишних действий, ошибок, дублирования и ненужной сложности.
